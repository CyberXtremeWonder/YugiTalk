## 2. 从这段对话理解 Vibe Coding

在这个项目里，你的作用不只是给 AI 发指令，还包括确定目标、修正取舍、观察运行结果并决定是否验收。AI 可以写代码和运行检查，但你仍需要看懂系统的入口、数据流、关键依赖和失败边界，才能判断生成的结果是否符合目标。

你多次通过截图和真实运行错误推动改进，这是有效的反馈。不过，截图只能说明现象。例如“添加成员失败”可能来自表单、接口参数、权限、用户不存在或服务不可用。更完整的反馈会显著减少来回修改：

> 当前版本、访问地址、账号角色 → 操作步骤 → 实际结果 → 期望结果 → 相关错误与日志。

你后期提出的 RAG 七步流程比“做一个高级 RAG”明确得多：规定了算法、分支、并发、次数上限、失败处理和恢复方式。这种表达可以直接转成实现任务和测试用例。

## 3. 把描述升级成可执行需求

### 从感觉到状态

“像 DeepSeek”“有科技感”可以作为参考，但应该接着写出具体行为。例如：

> 左侧为导航与会话列表，右侧只显示当前页面。默认浅色，Logo 左上角。聊天输入框固定在内容区底部，消息列表单独滚动。聚焦时没有黑色边框。生成中发送按钮切换为停止按钮，点击后停止该任务。

这样可以验收布局与交互；如果只有风格词，AI 容易生成视觉上不同但自认为符合要求的页面。

### 从“支持”到边界

“支持文件夹上传”应补充：哪些文件类型、单文件大小、数量限制、是否保留相对目录、同名与重复文件如何处理、部分失败是否影响成功文件、刷新后能否看见进度。

“支持本地和服务器模型”应拆成：聊天模型与嵌入模型分别支持哪些协议；本地模型如何定位；默认值；维度校验；缺模型是否允许下载；更换模型后旧索引怎样处理。测试环境不设额度也应明确为环境配置，不能变成所有环境永久关闭控制。

### 从“做好了”到证据

每个交付都应写明：改了什么、运行了哪些检查、真实依赖还是 Mock、结果在哪里、哪些没有验证、怎样人工验收。单元测试通过不能代替真实 Milvus 检索；Mock 回答成功不能证明 DeepSeek 联调成功；页面截图不能证明删除后向量已撤销。

## 4. 推荐的推进节奏

1. **先对齐当前状态。** 给出需求文档、最近阶段报告和当前任务；要求先检查代码与配置，不凭对话猜测实现。
2. **一次完成一个可验证闭环。** 例如“上传 → 解析 → Embedding → 入库 → 检索 → 引用”，每阶段限定范围。
3. **先写验收标准再实现。** 同时定义成功、空状态、失败、超时、取消与恢复，不只覆盖正常路径。
4. **要求实际测试。** 算法与状态逻辑用单元测试，服务边界用集成测试，用户交互用浏览器测试，数据变更用迁移与恢复验证。
5. **亲自走一遍关键路径。** 使用自己的账号、真实资料和模型，查看工具流程、引用来源和错误状态。
6. **沉淀结果再推进。** 更新 README、需求、阶段报告；完成项目范围内的缓存与镜像检查；你确认验收后进入下一阶段。

不必每次都跑所有测试。让 AI 解释检查与改动的关系，选择能发现本次风险的检查；数据迁移重点验证一致性与恢复，字体改动重点验证视觉与布局。

本次 PowerShell 编码问题提供了一个具体提醒：只说“支持 Windows”还不够。开发助手使用 PowerShell 7 时，无 BOM 的中文脚本可以解析，但你使用 Windows PowerShell 5.1 时可能按系统编码误读。可以在提示词中补充“同时验证 Windows PowerShell 5.1 和 PowerShell 7，中文 `.ps1` 使用 UTF-8 BOM”，并要求提供版本与实际运行证据。修复记录见 [双版本编码验收](./stages/artifacts/powershell-encoding-check.json)。

## 6. 本项目最值得进一步掌握的内容

- **数据位置：** PostgreSQL 保存账户、任务、分块和检查点；Milvus 管理向量；MinIO 保存上传原文及 Milvus 对象；etcd 保存 Milvus 元数据；Redis 保存队列等运行数据。模型权重不等于知识库向量。
- **任务可靠性：** 请求成功不等于任务成功。理解排队、Worker 执行、租约、检查点、重试、幂等账本与取消之间的关系，才能解释为什么恢复不会简单重复所有步骤。
- **RAG 评测：** 检索命中、证据足够与回答可信是不同问题。需要固定评测资料、问题与正确来源，比较简单检索和复杂路由的效果与成本。
- **范围与成本：** 你要求复杂问题最多 2–4 个子问题，重写与复评最多各一次，是可以测试的预算边界；同样应给 Rerank 定义输入限制、deadline 与熔断条件。
- **部署和数据保护：** 改 Compose 并不自动迁移旧数据。镜像、卷、bind mount、下载缓存和数据库备份各有用途；不能用全局清理代替迁移。

当前阶段 0–5 已人工验收，阶段 6 生产完善开发中；完整七步 RAG 于 2026-10-11 实现并通过自动验证，本轮人工验收待确认。正式生产部署、安全加固和真实模型质量仍需完成独立验收。

登录密码长度调整同时落实到页面输入、后端契约和账号初始化，并用实际哈希登录验证短密码、长密码及中文内容。表达这类需求时可以补充“完整输入不截断、现有密码不重设、错误凭证仍返回统一提示”，让前后端和管理入口保持一致。

这次改进体现了三个有效的 Vibe Coding 做法：先用“2–4 个子问题、最多一次重写、一次复评”把抽象目标变成可测试边界；明确本地 SuperMew 参考位置，让实现依据真实代码并复用本项目权限与预算；要求真实 Milvus 验证，而不只看模拟测试。实际集成发现并修正了 REST 建集合字段与服务端结构不一致的问题，这说明“接口返回成功”也必须继续核验字段、索引及真实写入。

下一次可以在需求里同时给出正常例、失败例、次数上限、数据版本与验收证据。例如：“澄清必须恢复同一个 Run，重载后可从历史恢复；重复提交幂等；删除资料或撤销成员权限后拒绝恢复。”这类表达能直接对应自动测试，也更容易在面试中解释设计取舍。现有集成证明链路能执行，正式模型评测才能证明答案质量；两种验收分别记录。

## 7. 面试时怎样讲这个项目

按“问题 → 取舍 → 实现 → 证据 → 局限”来讲。例如：

> 用户上传资料后需要知道异步处理是否完成。我把流程分成解析、分块、Embedding 和入库，通过持久状态展示进度与失败步骤；检索前以数据库的可用状态和索引版本过滤资料。验收覆盖上传、删除及真实向量检索。复杂路由、BM25 混合召回与结构化 Grader 是后续改进，不能当作当前已经完成的能力。

准确说明自己为什么提出这些约束、如何验收和哪里还不足，比单纯罗列框架名称更容易展示你对工程的理解。

你追加“知识库查不到就回复没有相关知识，不回复模型通用知识”，把拒答行为变成了明确的产品规则。验收应同时覆盖空库、无关资料、一次纠错仍不足，并确认不调用通用回答模型、没有伪造来源；服务故障仍显示错误，不能当作无结果。调试真实模型前限定一次请求、证据数量、片段长度和输出上限，也能让隐私授权与诊断成本保持具体可核对。

“下拉框展开自然、点击不显示红框”可以进一步描述为：菜单圆角、轻阴影、颜色与主题一致，鼠标点击不增加轮廓，但键盘导航仍有清晰焦点；验证选择、点击外部收起、浅深色主题和窄屏。视觉偏好加上这些交互状态，能减少反复修改，也避免为了外观误删键盘可访问性。当前本机浏览器支持可定制原生菜单；不支持的浏览器保留原生选择功能和无红框点击样式，菜单外观可能不同。

## 8. 本次生产完善带来的改进方法

你追问 Prompt 注入，并要求代码讲解，能把“有安全提示词”推进到可验证的工程边界。以后可以明确：“恶意 Skill、知识库、记忆和旧检查点不能获得系统角色；模型诱导的越权工具连缓存结果也不能返回；流式和历史回复不得自动请求外链图片；测试需分别说明程序限制与真实模型抗攻击能力。”JSON 和内容哈希各有作用，不能把格式完整或版本未篡改误当成正文安全。

新增 Skill 的需求可以从“参考 SuperMew”进一步明确为：“元数据、正文和工具许可分开；目录只加载摘要；每次任务选一个技能；版本和内容哈希冻结；权限只能收窄；禁用或删除后禁止继续和恢复；无知识证据仍拒答。”这让参考项目成为可核对的设计依据，而不是只复制页面。

本次明确区分了三层验收：离线单测证明服务端边界，真实页面加真实 API 证明操作链路，正式模型评测才能证明流程说明的执行质量。面试可解释为什么采用不可变版本和授权交集，以及为什么 Mock 成功不等于真实模型输出质量达标。

把“可上线”拆成可核对的条件：独立凭证和数据目录、合并后的Compose、HTTPS真实流式、业务恢复、固定镜像回滚、安全报告与完整负载。依赖无漏洞不能替代镜像扫描；文件复制成功不能替代原文、向量和账户恢复；短测通过不能替代30分钟稳定性。要求AI同时保留通过、失败、未执行三种状态。

调试时先保存首轮失败的前后证据。恢复演练第一次只留下失败类型，缺少原始差异，导致无法确定根因；后续保存完整指纹再复验。镜像操作也应要求使用实际ID，并明确是否兼容当前Schema，不能把可变标签当作回滚保证。

可以这样提需求：“每次生产改动同时给出已实现子项、实际验证范围和未通过门槛。保留新旧扫描与延迟原始数据，明确冷连接、预热连接和模型耗时。失败后自动恢复已验证环境；数据库不做未经演练的降级。任何未执行项不得写通过。”

阶段6续开发进一步说明：性能目标要同时指定并发、持续时长、资源配置、暖机方式和计时起点。把一次请求拆成提交、排队、模型首段和页面读取，才能判断优化方向；提高CPU容量应单独标明，不能全部归功于代码。短测与长测分别保存，重试验收用独立身份，既避免历史额度影响，又保留正式预算保护。镜像则先扫描候选，再验证迁移和恢复；“更新到新版本”与“安全通过”是两项不同证据。

你补充“镜像还包括Docker的”也体现了范围要明确：清理对象可以是Docker镜像、导出的扫描归档或依赖下载缓存，三者分别记录。要求先核对运行/停止容器、上一构建版、发布回退记录和备份清单，再删除确实无用途的项目版本；删除标签不一定释放镜像层，删除镜像也不能直接声称系统盘已回收同等容量。保留扫描证据、业务数据和既有BGE权重。

这次选择现有S3还说明：更换基础设施时，要同步说明原文、向量对象、本地元数据分别存在哪里，不能只改服务地址。缺少服务信息时先完成配置边界和协议测试，将真实认证、网络、恢复列为未验证；特别要求“备份范围必须包含远端对象，未完整验证不能发布”。你的需求因此从“换一个组件”推进到“连同权限、数据与恢复路径一起验收”。


你追加“回答不显示来源索引、取消对话额度限制”，说明同一个需求要覆盖新任务、流式增量、旧历史和不同部署环境。不要只删提示词里的引用要求或把额度调大：正文显示和证据身份分开处理，额度开关与用量记账分开处理，并明确保留超时、并发和工具次数。验收应确认分段输出不闪出半截索引、刷新后行为一致、来源原文仍可核对、超过原额度仍能执行且统计正确。


这次回答中断提醒你：先要求错误码、任务状态和实际输出长度，再判断是否是额度或网络问题。协议容量、正文容量和 Token 额度是三种边界，不能混为一谈。修复需求可以写为：保留超时、权限与异常大小保护，分别配置协议和正文上限，用离线碎片流复现，验证任务终态和用量保存；真实供应商验收单独记录，不能把替身通过写成线上问题已复验成功。

## 9. 将参考项目转化为工具管理需求

你追加“工具与用户绑定，非公共工具”把权限范围从空间收窄到了个人。可以进一步要求：“批准不改变所有者；同空间其他用户也不可见、不可授权、不可复用缓存或恢复调用；即使猜中工具名也必须拒绝。”验收应同时覆盖目录、HTTP接口与执行层，不能只隐藏页面按钮。

邮箱验证码与开发模式同样应拆开定义：验证码证明邮箱控制权，管理员身份来自服务端角色，开发模式只是受保护的界面和会话状态，不能赋予角色或关闭生产安全检查。明确SMTP未配置时的行为，并把内存邮件测试与真实送达区分记录，能减少“页面看起来完成，但实际服务未接通”的误判。

你提出“类似 SuperMew 的 Tool 管理”，再补充默认天气和路况，把抽象平台能力落到了实际使用场景。下一次可以一起说明：默认工具名称与真实数据来源、密钥由谁配置、未配置显示什么、哪些角色能修改，以及 Agent/Skill 怎样获得权限。目录注册、启用、配置就绪、任务授权是四个独立状态，不能把有按钮当作已能查询。

参考项目应落实为可验收规则：版本不可变；调用只用冻结 Schema；管理员停用后旧任务、缓存和检查点不能复活权限；域名在配置和实际 DNS 两层检查；真实 Key 不进入模型参数；工具失败不得编造实时数据。测试分为内存网络替身、真实 API 页面、真实供应商联调，分别记录通过与未执行。

本次先限定只读 GET 和标量参数，能清楚解释功能边界与安全取舍。以后扩展 POST、MCP 或执行代码时，应先补确认流程、副作用幂等、隔离及凭证策略，不能简单把 HTTP 方法或脚本路径开放给模型。面试可从“为什么既冻结版本又实时检查撤销”讲起：前者保证可复现，后者确保权限变化立即生效。

这次开发启动报“配置解析失败”，实际是域名数组写成了 Python 的单引号形式，而配置要求 JSON 双引号。后续可以提出：“提供可复制的配置样例和独立预检；错误明确到字段及修正方式；环境变量与配置文件两种来源都测试；密钥和原始配置不得出现在错误日志。”这能让环境问题在启动前被定位，也避免为了排查而泄漏凭证。

修正配置后工具仍失败，说明还要验证配置实际在哪个进程生效：本机 API 负责提交，Docker Worker 负责执行，二者可能加载不同时间的配置。可以要求：“更新配置时同步 API、Worker、Scheduler；只输出配置是否存在和就绪状态，不打印密钥；说明重启与容器重建的区别。”配置文件正确、进程已加载、供应商真实调用成功是三项不同的验收结果。

你决定“暂不恢复演练，先部署”，进一步明确了交付顺序。可以写成：“先交付首次部署文件、无写入预检和操作步骤；没有服务器时不假装已发布；部署成功只说明启动、存储和HTTPS检查通过，恢复与模型质量分别记录未验证；不要把首次部署和已有数据升级混在一起。”这样能缩小当前任务范围，也保留后续工作的准确状态。
