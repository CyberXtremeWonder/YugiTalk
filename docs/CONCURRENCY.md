# API 数据库准入与事件通知

本次改动修复集中访问时数据库连接等待占满同步线程的问题，并减少 SSE 的空闲数据库轮询。它不等于已经完成一万路模型生成或一万路 SSE 的容量认证。

## 数据库请求的生命周期

`DatabaseAdmission` 在协程中等待许可，等待者不占用同步鉴权线程。默认每个 API 进程同时允许 10 个数据库型请求，最多排队 100 个，目标等待上限 1 秒。队列满或等待超时返回 `503 / database_overloaded`，响应含 `Retry-After: 1`；它不是成功请求。

许可覆盖鉴权、业务路由及 Session 清理。`DB` 使用 FastAPI 的 function scope，因此在路由返回后关闭 Session、归还许可，再开始发送 StreamingResponse 正文。清理使用独立线程容量，取消请求也需要先清理数据库资源。SSE 后续每批补读使用同一个准入预算，但等待通知时不持有许可、事务或数据库连接。

默认池参数从隐式值改为显式配置。池等待超时由之前的 30 秒改为 5 秒，普通 API 更早由准入队列保护。不要用增加线程数或数据库连接数替代容量测量。

| 环境变量 | 默认值 | 含义 |
|---|---:|---|
| `APP_WORKERS` | 1 | Uvicorn 进程数；与热重载互斥 |
| `DATABASE_POOL_SIZE` | 5 | 每个引擎的常驻连接数 |
| `DATABASE_MAX_OVERFLOW` | 10 | 每个引擎的额外连接上限 |
| `DATABASE_POOL_TIMEOUT_SECONDS` | 5 | 获取连接的等待秒数 |
| `API_DATABASE_CONCURRENCY` | 10 | 每个 API 进程的数据库请求执行上限，不含排队者 |
| `API_DATABASE_QUEUE_LIMIT` | 100 | 每个 API 进程最多等待的请求数；0 表示不排队 |
| `API_DATABASE_QUEUE_TIMEOUT_SECONDS` | 1 | 准入等待秒数；事件循环过载时不能保证严格墙钟期限 |
| `RUN_EVENT_FALLBACK_SECONDS` | 5 | SSE 漏通知后的补读间隔上限，实际等待使用 80%～100% 抖动 |

`API_DATABASE_CONCURRENCY` 不能超过单池连接上限，启动时会校验。参数修改需要重启相应进程。依赖最低 FastAPI 版本提升到 0.121，以支持 function scope；锁定运行时版本未升级。

## SSE 通知与可靠性

1. `append_event()` 在业务事务中写入 RunEvent，并登记待通知的任务编号。
2. 最外层事务提交成功后才发布 Redis 通知；回滚不发布。通知只包含任务编号，没有正文、Cookie 或用户令牌。
3. 每个 API 进程使用一个 Redis Pub/Sub 连接，向该进程中对应任务的订阅者发送内存唤醒信号。不同 API 进程各自接收通知，不使用竞争消费组。
4. SSE 先登记订阅再读库，读取前清除唤醒标记，避免读库与等待之间的通知竞态；每批最多 100 条，有积压时立即继续读下一批。
5. PostgreSQL 的 RunEvent 与 sequence 是内容和游标的唯一事实来源。重复通知合并；漏通知、发布者崩溃或 Redis 断开时，依靠定期补读恢复，Pub/Sub 不提供持久交付保证。

每次补读仍重新检查数据库中的登录会话、用户状态及任务所有权，再读取公开事件。没有权限缓存，也不直接转发 Redis 消息中的正文。闲置流的撤权关闭可能等待一个补读周期及查询耗时；新内容必须先经过同样的权限复核。单批内容从查询到实际发送之间仍存在普通并发系统的时间窗口，没有承诺瞬时撤权。

Redis 发布连接按进程延迟创建、复用，连接与读写超时分别设置为 100 毫秒且不自动重试；失败后冷却 5 秒。通知失败不改变已经提交的业务结果。API 自动重连订阅。Redis 故障会增加交付延迟，正常任务提交对队列 Redis 的依赖与原有恢复语义保持不变。

当前测试环境使用的 SQLite 注入引擎不自动启动 Redis 订阅，避免单元测试连接外部服务；真实集成验收使用 PostgreSQL 和 Redis。

## 多进程与连接预算

生产 Compose 支持 `API_CPUS`、`API_MEMORY_LIMIT`，默认仍为 2 CPU、768 MiB；`.env.production.example` 提供 4 进程、4 CPU、2 GiB 的示例。示例每池 `3+3` 个连接、每进程数据库执行上限 4，属于需要按机器复验的部署配置，不会自动扩容现有实例。

以 4 个 API 进程、2 个 Worker 子进程、1 个 Scheduler 都使用 `3+3` 池为例，所有池的理论连接上限合计为 `7×6=42`，另外需要预留运维、迁移、其他客户端和滚动发布容量。多副本会继续乘上进程数；准入器是进程内保护，不是跨实例的全局数据库配额。

当前 Prometheus 内存请求指标和测试诊断快照按进程保存；多进程下单次抓取不是整个 API 服务的汇总。生产扩容时应配置可区分实例的采集或完善多进程指标，不能用单进程快照证明全局容量。

对话列表的最近活动时间聚合已限定到当前用户和账号的消息，避免每次列出一个人的对话都聚合所有用户的消息。保留原有最近活动排序、稳定游标和空对话创建时间回退，不新增表或索引。

## 验证

- 准入的队列上限、超时、取消、同步查询异常、非法连接预算。
- 事务回滚与嵌套提交、Redis 发布失败冷却、通知唤醒、漏通知补读、撤权不交付新内容。
- 真实跨进程 PostgreSQL／Redis／HTTP：100 条 SSE 的空闲查询数、断连续传、Redis 故障及恢复、事件不重不漏和资源归还。
- 与改前相同 Windows 发压客户端、用户数据及查询／修改比例；单进程、双进程及增加 CPU 后的结果分别保存。
