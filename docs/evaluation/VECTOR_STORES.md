# PostgreSQL/pgvector 与 Milvus 检索对照

新增中文金融、法律、医疗的真实生成回答测试见 [中文 RAG 与回答对照](CHINESE_RAG_GENERATION.md)，其中包含逐题回答、标准答案与完整证据。

日期：2026-11-08。在本机 Windows 受限执行环境中启动独立 Linux Docker 容器实测；不是远端专用基准机器。仅添加评测脚本和报告，没有修改业务数据库、应用配置或检索实现。

## 第一轮：项目现有中文综合语料

固定 38 份 Markdown、3,817 个章节子块、393 个 MIRACL 中文 dev 问题，复用同一批真实 BGE-M3 FP32、1024 维、CLS+L2 向量。候选语料是 3,786 个已标注正负段落的受限池，不是官方完整语料。dev 曾用于项目方案选型。

版本：PostgreSQL 16.15、pgvector 0.8.7、Milvus 2.5.14。两个数据库容器均限制 2 CPU；PostgreSQL 内存上限 2 GiB，Milvus 3 GiB。Docker/WSL2 总内存约 15.45 GiB。版本、镜像摘要和环境记录在输出目录。

精确方案为 PostgreSQL 顺序扫描余弦距离与 Milvus FLAT；近似方案均为 HNSW，M=16、efConstruction=64、查询 ef=100。pgvector 开启 strict_order 迭代扫描、关闭 JIT，并核验 HNSW 查询计划。Milvus 写入后 flush，等待 3,817 行索引全部完成，再 release/load，核验已加载段为 Sealed、有索引且行数完整。初始化阶段发现的 growing/sealed 切换会影响候选，初步结果已归档，不作为正式结论。

主对照使用冻结语料和同一写入客户端的 Milvus Session 读取。PostgreSQL 使用 READ COMMITTED。冻结语料下比较检索结果，不能推导存在并发写入时两者一致性语义等价。

所有方案召回 Top24，经相同生产 `rrf`、`materialize`、`pack_evidence`，得到 Top5、最多 5000 字符来源。SQL 授权与父子关系使用隔离内存 SQLite，共用相同元数据；这不衡量 PostgreSQL 将向量与业务元数据放在同库的关联查询优势。

### 检索延迟和邻居召回

每个方案先逐题预热，再随机交错执行三轮，共 1,179 次单并发请求。延迟包括原生客户端的向量序列化和往返，排除嵌入、BM25、SQL 证据物化、生成和浏览器渲染；因此不是 RAG 端到端耗时或生产分位数。

Milvus 使用 PyMilvus gRPC，PostgreSQL 使用 psycopg、文本格式向量参数。客户端与协议开销包含在结果中，不是纯距离计算内核对照；现有应用的 Milvus REST 调用开销也没有包含在内。

| 方案 | 精确 Top24 邻居覆盖率 | 客户端 P50 | 客户端 P95 |
| --- | ---: | ---: | ---: |
| pgvector 精确余弦 | 100.000% | 15.27 ms | 16.81 ms |
| Milvus FLAT / Session | 100.000% | 3.76 ms | 4.45 ms |
| pgvector HNSW | 99.926% | 2.36 ms | 2.73 ms |
| Milvus HNSW / Session | 99.947% | 3.03 ms | 3.53 ms |

邻居覆盖率使用同一 float32 输入的 float64 精确余弦基准，统计 Top24 集合交集比例。两种精确方案在全部 393 题上返回相同 Top24 集合；pgvector HNSW 有 7 题、Milvus HNSW 有 5 题与精确集合不同。各方案三轮共 1,179 次结果集合均与各自质量测量一致。

### 最终证据质量

| 方案 | 纯向量 Recall@5 | 纯向量 Hit@5 | 共用 BM25 后 Recall@5 | 共用 BM25 后 Hit@5 |
| --- | ---: | ---: | ---: | ---: |
| pgvector 精确 / HNSW | 80.28% | 93.89% | 64.91% | 84.48% |
| Milvus FLAT / HNSW | 80.28% | 93.89% | 64.91% | 84.48% |

Recall 为逐题标注引文完整出现在同文档单条最终来源中的比例，再取宏平均；Hit 为至少覆盖一条正例的问题比例。不能跨来源拼接，不等于回答准确率。

混合对照固定使用同一组 Milvus 原生 jieba BM25 Top24 候选，再与各自向量结果做 RRF60。这是隔离向量后端变量的控制实验，**不是 PostgreSQL 原生 BM25 或独立 PostgreSQL 全栈混合检索的实测**。BM25 耗时也不计入向量延迟表。

本批数据的固定等权融合将 Recall@5 降低约 15.37 个百分点，数据库替换没有改变最终质量指标。它提示应优先验证融合策略和候选排序；不能据此推导所有领域关闭 BM25 都更好。

### 一致性模式敏感性

固定抽取 50 题，Strong/Session 随机交错次序，两轮各 100 次 HNSW 请求：

| Milvus 模式 | P50 | P95 | 候选集合与主测一致 |
| --- | ---: | ---: | --- |
| Strong | 395.09 ms | 400.48 ms | 100/100 |
| Session | 2.79 ms | 18.04 ms | 100/100 |

这是本机部署上的可重复配置差异，不能把约 395 ms 等待解释为向量计算速度，也不能由冻结语料实验决定业务是否可以降低一致性要求。敏感性子实验样本和执行时序不同，不与主延迟表直接混算。

### 核验与产物

逐题独立重算 8 组共 3,144 条证据评分，全部一致；上下文字符预算、来源数、源文件 SHA-256 校验通过；脚本通过 Python 编译。完整原始候选、逐题来源、三轮延迟、查询计划、已加载段与参数哈希保存在 `outputs/vector-db-compare-20261108/`。

资源快照保留作环境记录。数据库同时保留精确和 HNSW 两套测试数据，Milvus 另有 BM25、etcd 和 MinIO；不是同等功能、单索引、稳定负载下的资源基准，因此不据此给出内存性价比排名。建表、导入和建索引时间也包含不同工作量，不作为公平性能排名。

脚本：`scripts/benchmark-vector-stores.py`；隔离 Compose：`outputs/vector-db-compare-20261108/compose.yml`。依赖安装在输出目录 `deps/`，没有改动项目虚拟环境。复现需保留原始语料和向量缓存；完成的 `summary.json` 默认阻止覆盖，重新实验应先归档完成产物。`--reset-isolated` 只重置固定测试端点中的指定测试表/集合。

## 跨领域扩展

按用户补充要求，使用 BEIR 四个领域的完整候选语料，组成 75,128 篇文档的混合库。每域从可核验的 test 标注中按种子 20261108 固定抽取 100 题，共 400 题，不按模型成绩挑题。

| 数据集 | 领域/任务 | 完整文档数 | 原始 test 问题数 | 本轮问题数 |
| --- | --- | ---: | ---: | ---: |
| SciFact | 科学论断与文献检索 | 5,183 | 300 | 100 |
| NFCorpus | 医疗健康检索 | 3,633 | 323 | 100 |
| FiQA | 金融问答检索 | 57,638 | 648 | 100 |
| ArguAna | 社会议题论辩、反论点检索 | 8,674 | 1,406 | 100 |

四个压缩包均通过 BEIR 官方 MD5，并保存下载 URL 和 SHA-256。ArguAna 有 5 题的正例目标不存在于官方候选库，记录完整 ID 后从其余 1,401 题中抽样；FiQA 的 38 个空白文档保持原样，避免静默改变完整候选库。各方案排除与问题同 ID 的文档，避免问题自身的匹配。该轮是固定抽样实验，不是完整 BEIR 官方分数。

标题和原文合并为一个检索文档，不使用项目父子展开。所有文本离线使用同一修订 BGE-M3、FP32、CLS+L2、最大 1024 tokens 编码，原文不按字符预截断；超出 token 上限的数量单独记录。两库复用完全相同的向量文件，不调用付费生成模型。

本轮实际截断 399 篇文档：SciFact 20、NFCorpus 9、FiQA 356、ArguAna 14；400 个问题均未截断。编码初始批次为 16，长文阶段接近 16 GiB 显存上限后，从已刷盘的排序前 73,616 行检查点以批次 4 续算，保留 FP32。恢复前核验输入文件哈希和已有向量归一化；`encoding.json` 的耗时只覆盖恢复阶段，不用它宣称全量编码提速。

三种过滤范围：全库；仅当前领域；仅当前领域内按文档 ID 哈希得到的约 1% bucket。bucket 由一条正例所属桶确定，确保至少存在可见正例；评分标注限制到可见文档。这是人工访问范围实验，不是真实租户分布，且不能把缩小分母后的指标上升当成检索质量提升。

pgvector 使用 HNSW、`(domain,bucket)` B-tree、默认优化器和 strict_order 迭代扫描；记录各域各场景的实际查询计划，允许优化器在严格过滤时选择标量索引和精确排序。Milvus 配置 HNSW、domain/bucket INVERTED 标量索引，写入后封存、完成索引并重新加载；Session 读取冻结数据。HNSW 参数仍为 M=16、efConstruction=64、ef=100，不逐域调参。

每题召回 Top24、评估 Top10，不设本轮的相似度阈值；计算相关文档 Recall@10、Hit@10、线性标注增益的 nDCG@10，以及相对精确余弦 Top24 的邻居集合覆盖率和不足量返回次数。另用同一组 Milvus 原生 standard tokenizer BM25 候选进行 RRF60 控制对照，仍不代表独立 PostgreSQL BM25 实现。

每题先预热，再随机交错后端执行三轮；延迟仅包括原生客户端向量查询和序列化，不包含 BM25、精确基准、评分或生成。该轮指标与第一轮的引文完整覆盖率定义不同，不直接横比。

各领域原始相关性标注没有额外增加跨数据集的交叉相关性人工判断。全库混合场景将其他领域作为干扰候选；按领域过滤场景更接近原数据集完整候选范围。只构建一轮索引，三轮重复的是查询，没有测量索引重建随机性、并发写入或高并发吞吐。

脚本：`scripts/benchmark-vector-domains.py`；阶段为 `prepare`、`encode`、`evaluate`。数据及结果位于 `outputs/vector-domain-compare-20261108/`。

### 跨领域主结果：仅当前领域过滤

下面每域 100 题，延迟来自 300 次重复查询；质量为纯向量 Top10。PostgreSQL 使用默认优化器，其代表性 EXPLAIN 显示科学、医疗、论辩领域采用标量索引后精确排序，金融采用 HNSW，因此不能把整表描述为两种 HNSW 实现的纯内核竞争。

| 领域 | pgvector Recall@10 | Milvus Recall@10 | pgvector nDCG@10 | Milvus nDCG@10 | pgvector P50/P95 | Milvus Session P50/P95 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 科学 SciFact | 75.60% | 74.60% | 0.5909 | 0.5866 | 14.41 / 19.96 ms | 3.06 / 20.59 ms |
| 医疗 NFCorpus | 15.59% | 15.54% | 0.3198 | 0.3185 | 10.30 / 12.87 ms | 2.95 / 4.05 ms |
| 金融 FiQA | 49.71% | 49.21% | 0.4441 | 0.4404 | 2.98 / 3.55 ms | 3.28 / 3.99 ms |
| 社会议题 ArguAna | 82.00% | 82.00% | 0.5443 | 0.5430 | 21.45 / 23.32 ms | 2.88 / 3.47 ms |

这是不同计划的质量/延迟取舍。不能只报 Milvus 的中位数优势：科学场景中 Milvus 的 P95 为 20.59 ms，并未优于 PostgreSQL 的 19.96 ms；金融场景本轮 PostgreSQL 更快。

各领域、各过滤场景和两种融合模式的 Recall/nDCG 配对 bootstrap 95% 区间均跨零或包含零，本轮没有证明召回质量存在稳定优劣。区间为 10,000 次配对重采样、探索性比较，未作多重比较校正，也未包含索引重建随机性。不同领域的正例数量不同，尤其医疗每题可有多个正例，不按跨领域 Recall 百分比直接给模型排名。

### 全库与严格过滤

全库混合检索时，pgvector P50 为 2.70–3.03 ms，Milvus Session 为 3.06–3.30 ms；原始 HNSW Top24 邻居集合覆盖率按领域为 pgvector 76.50–99.75%、Milvus 80.50–99.92%。集合指标与标注相关性指标不同，近似索引参数和重复/近似并列文档也影响严格 Top24 集合交集，不能把邻居差异直接当成回答错误。

领域内约 1% bucket 的结果：

| 领域 | 平均可见文档数 | pgvector P50 | Milvus Session P50 |
| --- | ---: | ---: | ---: |
| 科学 | 约 52 | 1.40 ms | 1.87 ms |
| 医疗 | 约 37 | 1.34 ms | 1.91 ms |
| 金融 | 约 577 | 3.38 ms | 2.38 ms |
| 社会议题 | 约 88 | 1.53 ms | 1.97 ms |

该范围内两库邻居集合覆盖率均为 100%，相关性指标也相同。所有主场景都没有不足量返回，判断标准为 `min(24, 可见文档数)`，并非强求不足 24 个可见文档时也返回 24 个。三轮全部 7,200 次查询的候选顺序与各自质量测量一致。

### PostgreSQL 查询计划补充诊断

为确认默认排序不是不可调整的数据库能力限制，另用两个连接交错比较默认计划与明确要求 HNSW 的计划。两者均关闭自动 prepared/generic plan（`prepare_threshold=None`），每域 100 题、每模式 300 次测量；强制模式仅在自己的连接关闭 bitmapscan、seqscan 和 sort，并以 EXPLAIN ANALYZE 确认 HNSW。没有修改数据库全局参数或业务配置。

| 领域 | 默认 P50 | 强制 HNSW P50 | 默认 Recall@10 | 强制 HNSW Recall@10 | 强制 HNSW P95 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 科学 | 13.10 ms | 2.44 ms | 75.60% | 72.60% | 6.10 ms |
| 医疗 | 9.71 ms | 2.64 ms | 15.59% | 14.18% | 47.99 ms |
| 金融 | 1.96 ms | 1.85 ms | 49.71% | 49.71% | 2.36 ms |
| 社会议题 | 21.17 ms | 2.10 ms | 82.00% | 82.00% | 2.73 ms |

这组独立诊断排除了向量序列化时间，不将其绝对耗时与主实验 Milvus 表格直接拼接比较。强制 HNSW 在科学、医疗出现召回损失，医疗尾延迟约 48 ms；不能把单个开关包装成无代价的通用提速。完整脚本、逐题结果和计划在 `pg-plan-control.py/json`。

### 混合检索不是跨领域通用增益

按领域过滤，使用共用 BM25 的控制对照：

| 领域 | pgvector 纯向量→混合 nDCG@10 | Milvus 纯向量→混合 nDCG@10 |
| --- | ---: | ---: |
| 科学 | 0.5909 → 0.6245 | 0.5866 → 0.6214 |
| 医疗 | 0.3198 → 0.3219 | 0.3185 → 0.3212 |
| 金融 | 0.4441 → 0.3938 | 0.4404 → 0.3937 |
| 社会议题 | 0.5443 → 0.4853 | 0.5430 → 0.4853 |

科学和医疗点估计改善，论辩下降；金融 Recall 略升但排序质量下降。结合第一轮中文引文实验，不能概括为 BM25 总是有效或总是无效，需按业务任务评测融合策略。这也不是 PostgreSQL 原生 BM25 与 Milvus BM25 的比较，因为两者使用同一组词法候选。

### 验证与适用边界

独立核验全部 4,800 条逐题评分、7,200 次延迟、48 个汇总分组、可见范围和问题自身排除、文件及脚本哈希，通过。`verification.json`、`paired.json`、`summary.json` 和原始逐题文件保留在输出目录。

补充 PostgreSQL 计划对照的 800 条评分、2,400 次计时也通过独立核验。测试结束已停止四个专用数据库/依赖容器，原始语料、向量、测试数据与结果保留；没有切换业务向量库或修改生产配置。

实测支持：在这批数万级文档上，两者都能满足低毫秒级的部分检索场景，默认计划、过滤范围、一致性模式和融合策略会改变表现。现有结果没有支持用“Milvus 的 RAG 回答更准”排除 pgvector，也没有证明 pgvector 在所有过滤负载下更快。它不是生成答案准确率、独立 PostgreSQL 全栈混合检索、百万级语料、高并发或生产部署认证。
