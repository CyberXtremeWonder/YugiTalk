# 3,000 用户访问验证

日期：2026-11-08。结果目录：`outputs/users-3000-20261108/`。

沿用上一轮最终配置：API 4 个 Uvicorn 进程、4 CPU 配额、2 GiB 内存；每进程连接池 `3+3`、数据库执行并发 4、队列上限 100、准入等待目标 1 秒。PostgreSQL 为 2 CPU、2 GiB，Redis 为独立测试实例。本轮业务源码与上一轮最终容量测试的指纹一致，没有改业务代码。

每轮 3,000 个独立已登录用户，各发一次请求：2,400 次读取本人对话列表、600 次修改本人对话标题。使用原 Windows aiohttp 发压函数，通过本机 HTTP 端口进入隔离 Linux API；每轮重启 API 并预热 40 次，预热不计入结果。

| 场景 | 目标到达速率 | 成功 | HTTP 503 | HTTP 500／客户端错误 | 成功 P95 | 成功 P99 |
|---|---:|---:|---:|---:|---:|---:|
| 30 秒均匀到达 | 100 请求/秒 | 3,000 / 3,000 | 0 | 0 | 14.4 ms | 22.0 ms |
| 所有任务同时调度 | 不设固定 RPS | 415 / 3,000 | 2,585 | 0 | 4.212 s | 4.234 s |

均匀访问轮次耗时约 30.006 秒，成功吞吐约 99.98 请求/秒；全部响应通过本人对话及预期标题校验。

突发轮次耗时约 4.592 秒，成功率约 13.83%；2,585 个 503 均为 `database_overloaded`。全部请求 P95 为 3.803 秒，其中包含过载响应，不能作为正常服务时延。客户端调度偏差 P99 约 1.066 秒，因此这是同时调度客户端任务的突发测试，没有证明服务器在同一个时刻处理了 3,000 个请求。

两轮所有请求的状态、错误及独立用户条数均核对通过；所有 200 响应的数据校验通过。突发后使用正常读取验证恢复，状态 200、数据校验通过，耗时保存在 `recovery.json`。过载响应是保护措施，不能计为成功服务。

本轮每种负载只运行一次。结论是：当前配置通过 3,000 用户在 30 秒内均匀访问的场景；未通过 3,000 客户端任务同时调度的突发场景。不包含密码登录、Nginx／TLS、SSE、RAG、embedding、rerank、模型生成或长时间稳态验证。

复现脚本为 `scripts/verify-3000-users.py`。它复用上一轮隔离测试数据库中的用户并生成新的独立有效会话，只选择前三千人发压，结果另存且拒绝覆盖。本轮没有重新播种或修改业务数据库。运行前须启动上一轮隔离项目及其 `capacity.yml` 配置。

原始文件：

- `paced-3000.json`、`burst-3000.json`：逐请求结果及进程内诊断采样。
- `summary.json`：两轮汇总。
- `manifest.json`：源码 SHA-256、配置及范围。
- `runtime.json`：实际镜像、进程命令、资源及连接配置核对。
- `verification.json`：6,000 个请求的结果核对。
- `recovery.json`：突发后恢复检查。
- `api.log`：本轮隔离 API 日志。
- `stopped-containers.json`：三个测试容器的停止状态。

多进程诊断采样来自单次请求命中的进程，未按 PID 全局汇总；本报告不使用该采样宣称全局并发峰值。
