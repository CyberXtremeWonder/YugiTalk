# 数据库准入、SSE 通知与 API 扩容实测

日期：2026-11-08。结果目录：`outputs/concurrency-improvement-20261108/`。

## 已完成的改动

- 在数据库鉴权前异步、有界排队，覆盖整个请求数据库会话的生命周期；过载返回 `503 / database_overloaded` 和 `Retry-After: 1`。
- 请求 Session 在路由返回后清理，SSE 等待通知时不占数据库连接和准入许可；每批补读重新鉴权。
- RunEvent 事务提交后发送 Redis 唤醒，API 每进程一个订阅连接；数据库仍负责内容、顺序及断线补读。
- Redis 故障或漏通知时，默认约 4～5 秒间隔补读；恢复后自动重订阅。
- 对话列表聚合消息时间时先限定当前用户及账号，保持原排序、游标和私有资源边界。
- 显式配置连接池，增加 `APP_WORKERS` 及生产 API CPU／内存配置入口；不自动部署或扩容现有服务。

具体配置、事务及权限语义见 [并发配置](../CONCURRENCY.md)。

## 普通 API 的同路径对照

均使用相同 Windows aiohttp 请求函数、10,000 个真实独立已登录测试用户、80% 对话列表查询及 20% 修改本人对话标题。每人请求一次，30 秒均匀到达，目标约 333.33 请求/秒。API 镜像运行时相同，挂载对应轮次的工作区源码；没有额外 HTTP 监控中间件或连接池方法包装。

| 配置 | API 资源 | API 池总上限 | 成功 / 10,000 | HTTP 500 | HTTP 503 | 客户端超时 | 成功 P95 |
|---|---|---:|---:|---:|---:|---:|---:|
| 改前 | 1 进程、2 CPU、2 GiB | 15 | 22 | 80 | 0 | 9,898 | 32.568 s |
| 准入＋通知＋限定查询 | 1 进程、2 CPU、2 GiB | 15 | 4,683 | 0 | 5,317 | 0 | 0.814 s |
| 同代码，调低单进程执行并发 | 2 进程、2 CPU、2 GiB | 30 | 9,068 | 0 | 932 | 0 | 0.789 s |
| 扩容配置，每进程执行并发 4 | 4 进程、4 CPU、2 GiB | 24 | 10,000 | 0 | 0 | 0 | 0.072 s |

四进程配置为每池 `3+3`、每进程数据库执行并发 4、每进程排队上限 100、准入等待目标 1 秒。PostgreSQL 独立容器为 2 CPU、2 GiB；Redis 为 128 MiB 内存上限。最终配置实测成功吞吐约 **333.13 请求/秒**，P50 **21.6 ms**、P95 **72.0 ms**、P99 **149.1 ms**，最大 **305.9 ms**；所有响应均通过本人对话及标题校验。

这不是纯代码优化对照：最后一轮增加了 CPU 和 API 进程数。单进程的 503 是正确的过载保护，但仍代表请求未被成功服务。不能把保护生效写成容量达标。

热点查询优化前，只有准入与通知的单进程轮次成功 4,723 次；限定查询后为 4,683 次，未见整轮吞吐改善。`query-plans.json` 中一次暖缓存 `EXPLAIN ANALYZE` 对照为 3.440 ms → 0.022 ms，结果一致，说明扫描工作量减少，但该数字不是可重复的吞吐提升倍数，也没有消除 API 进程的吞吐瓶颈。

## 瞬时突发与限制

单进程最终查询版本中：1,000 个同时调度任务有 27 次成功、973 次 503；10,000 个同时调度任务有 21 次成功、9,979 次 503。两进程中，1,000 个同时调度任务有 159 次成功、841 次 503。上述轮次没有 500、客户端错误或数据校验失败，但不能视为成功承载这些突发请求。

万人突发下 Windows 发压调度本身有秒级偏差，API 事件循环也会承受接入及拒绝响应的成本；准入等待参数不是过载时严格的墙钟截止时间。没有对四进程配置执行万人瞬时突发或长期稳态验证。

“10,000 用户在 30 秒内各请求一次”不是“服务端同时处理 10,000 个请求”，也不是“10,000 路模型生成”。这些目标需要单独验收。

## 真实 SSE／Redis 验证

生产者在 Windows 进程中提交 PostgreSQL 事务，通知经独立 Redis 容器送到 Linux API，消费者通过真实 HTTP 读取 SSE；不调用模型。100 个独立用户及任务参与验证。

| 项目 | 单 API 进程 | 四 API 进程汇总 |
|---|---:|---:|
| 100 条流空闲两秒新增 SQL | 0 | 0 |
| 空闲样本借出的数据库连接 | 0 | 0 |
| 提交开始至 100 个客户端均收到事件 | 0.609 s | 0.325 s |
| Redis 停机后全部依靠补读收到事件 | 4.192 s | 4.183 s |
| Redis 恢复并结束发布冷却后全部收到事件 | 0.679 s | 0.339 s |
| 断线后使用游标补读的客户端 | 5，全部通过 | 5，全部通过 |
| 会话撤销后禁止交付新正文 | 通过 | 通过 |
| 重复或缺失事件 | 0 | 0 |
| 结束后订阅者／借出连接 | 0 / 0 | 0 / 0 |

这里的交付时间包含生产者的批量数据库更新、提交及最后一个客户端收到事件，不能解释为单次 Redis 延迟。各场景只运行一次，不比较单进程与四进程延迟的统计显著性。

四进程测试按 PID 汇总四个工作进程的快照，不能用单次 HTTP 抓取的单进程指标代替汇总。最初的采样尝试因连接分发偏斜未覆盖全部进程而中止；扩大独立采样连接后覆盖全部四个进程，随后完成所有事件交付断言。
