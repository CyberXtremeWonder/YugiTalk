# YugiTalk RAG 调优方案与参数位置

本方案按当前代码编写。表中是源码默认值，不是对私有 `.env` 或运行中容器实际配置的判断。已完成的 MIRACL 训练集候选池对照见 [全量实验结果](../../outputs/miracl-zh-sections/RESULTS.md)，分块问题与代码修改见 [实现说明](../../outputs/miracl-zh-sections/README.md)。实验创建独立新索引，未替换旧库或更改业务默认参数；实验结果不能直接视为真实业务集效果。

本轮 1312 题结果：原固定窗口 Recall@5 56.66%，按小节隔离后 67.22%，再加本地重排达到 85.10%。重排候选 36 / 48 分别为 85.20% / 85.32%，收益较小；上下文 5000 / 6500 / 8000 和阈值 0.30 / 0.35 / 0.40 在本轮相同候选数下结果一致。优先建议小节边界策略加重排，保留候选 24、上下文 5000、阈值 0.35，再用独立验证集检验。未重排时，候选增至 36 / 48 反而降至 66.06% / 65.53%，说明扩大候选不能代替最终排序。

## 1. 先固定基线

先完成 [检索评测标注](./RETRIEVAL_EVALUATION.md)，再调整参数。建议准备 50–100 个真实业务问题，分开统计直接事实、换种说法、精确术语、跨文档关系、同名歧义和无答案问题。跨文档题须标注全部必要证据；另保留一部分题作为最终验证集，避免根据同一组题反复调参而过拟合。

固定知识库资料与索引版本、问题集、证据标注、模型及服务版本。每次只改一个参数，在相同条件下运行；耗时比较先预热，再重复三轮，避免把第一次加载模型的时间当成稳定性能。

```powershell
$env:PYTHONUTF8='1'
backend/.venv/Scripts/python.exe scripts/evaluate-knowledge-retrieval.py --cases outputs/rag-evaluation/labeled-cases.json --output outputs/rag-evaluation/baseline
```

重点观察 Recall@5、完整证据命中率、Hit@1（通过 `--k 1` 另跑）、负例空结果率和 P95，同时看完成率。正例少于 K 个标注证据时 Precision@K 不一定能达到 100%，不要把它当成唯一目标。

当前脚本测的是搜索接口最终证据。它包含 Dense、BM25、图谱融合、父级合并和证据打包，**不执行聊天中的重排、问题分解、Grader、纠偏和生成答案**。调整这些聊天阶段后，应另用完整对话评测；现有 `backend/evaluate_rag.py` 调用完整对话，但当前只做 exact_match，不能直接用它衡量语义质量或召回提升，且会调用配置的聊天模型。

## 2. 参数在哪里改

应用配置定义：`backend/app/core/config.py`。

- 本机 Python：编辑项目根目录 `.env`，重启处理请求的 API 和 Worker；进程环境变量优先于 `.env`。
- Docker：根目录 `.env` 供 Compose 替换变量，是否进入容器还要看 `docker-compose.yml` 的后端 environment；生产覆盖见 `docker-compose.prod.yml`。修改已经透传的值后需要重新创建服务，单纯 `restart` 不会更新容器环境。
- `backend/.env.rag-test` 只控制评测脚本连接哪个服务、使用哪个账号和知识库，不控制服务端 RAG 参数。
- 改源码默认值后，已有 `.env` 或容器变量可能仍覆盖它；Docker 运行的代码还必须重新构建对应镜像。

对于已运行且代码版本一致的开发环境，修改已透传的环境参数后，可按现有开发流程更新容器，例如：

```powershell
docker compose -p yugitalk-dev up -d --no-deps --force-recreate api worker scheduler
```

这会短暂停止对应服务，先确认当前没有需要保留执行中的任务。若尚未部署图谱代码，先按 [开发端启动说明](../DEVELOPMENT.md) 构建新镜像、执行迁移并启动依赖，不能只执行上面的重建容器命令。

### 直接可配置的主要参数

| 参数 | 源码默认值／范围 | 实际影响 | 建议实验 | 是否需重建索引 |
| --- | --- | --- | --- | --- |
| `RAG_CANDIDATE_LIMIT` | 24；5–48 | Dense/BM25 每路返回上限、第一次融合截断及图谱融合候选上限；不是最终来源数 | 24 → 36 → 48，观察最终证据召回与 P95 | 否 |
| `RAG_CONTEXT_CHARACTERS` | 5000；700–8000 | 最终证据总字符预算，超出会截断 | 5000 → 6500 → 8000，针对“命中文档但引文被截断” | 否 |
| `RAG_MERGE_RATIO` | 0.5；大于 0 且不超过 1 | 命中子块达到覆盖率后替换成父块，另要求至少两个子块 | 0.5 与 0.8 对比，看长上下文是否挤掉另一份必要证据 | 否 |
| `RAG_GRAPH_ENABLED` | true | 是否构建及使用图谱，前提是文档有可用图谱 | false / true，同一批多跳题对照 | 关闭不需；启用须先构建图谱 |
| `RAG_PARALLEL_QUERIES` | 4；1–4 | 复杂问题子查询并发；不改变最多 4 个子问题的上限 | 资源紧张时试 2；主要影响耗时和负载 | 否 |
| `RAG_TIMEOUT_SECONDS` | 60 秒；1–180 | 整个 RAG 执行截止时间 | 确认超时原因后再试 90；不是质量阈值 | 否 |
| `RAG_FAST_MODEL` | 空 | 复杂问题规划、纠偏和图谱抽取使用的模型，空时沿用默认模型 | 先保持，再比较可靠且更快的已有可用模型 | 普通检索不需；图谱抽取模型变化后要重建图谱才能比较新抽取效果 |
| `RAG_GRADER_MODEL` | 空 | 证据是否充分、歧义及路由判断，空时沿用默认模型 | 证据已正确但经常误拒答时单独评估 | 否 |
| `RAG_FAST_API_KEY` / `RAG_GRADER_API_KEY` | 空，沿用 `MODEL_API_KEY` | 角色独立凭证，仍使用统一供应商与地址；不进入任务快照 | 使用同一接口地址下对应角色可访问模型的密钥 | 否 |
| `RAG_RERANK_URL` / `MODEL` / `API_KEY` | 空，默认不重排 | 聊天流程的 HTTP 重排；不会增加新证据 | 融合候选有答案但排名靠后时再启用 | 否 |
| `RAG_RERANK_MAX_CHARACTERS` | 12000；700–24000 | 真正送入重排的候选总文本量，每条最多 2000 字符 | 确认重排覆盖不足后试 18000 / 24000 | 否 |
| `RAG_RERANK_TIMEOUT_SECONDS` | 3 秒；大于 0 且不超过 15 | 重排超时，失败回退原排序 | 先保留 3；服务正常但频繁超时时再试 5 | 否 |
| `RAG_RERANK_FAILURE_THRESHOLD` / `COOLDOWN_SECONDS` | 3 次 / 30 秒 | 服务故障熔断恢复，属于可用性参数 | 不作为召回调优手段 | 否 |
| `EMBEDDING_MODEL` / `REVISION` / `DIMENSION` | BGE-M3／固定 revision／1024 维 | 向量空间和索引版本身份 | 数据质量、分块和候选已排查后再比较模型 | 是，重新生成向量并发布兼容索引 |

这些环境变量在模板 `.env.example` 中可找到主要配置，在 Compose 中已透传上表的 RAG 参数。不要把“候选 48”误解为“回答引用 48 条”：最终来源数量目前固定最多 5 条。

### Dense 相似度阈值的特殊情况

`RETRIEVAL_MIN_SCORE` 定义于 `config.py`，默认 0.35，范围 0–1；`retrieval.py` 用它过滤 Dense 余弦相似度。BM25 走自己的正分过滤，图谱也不使用该阈值，所以调高它不保证所有无关结果都消失。

候选实验可用 0.30、0.35、0.40：漏召回多时尝试降低，无关候选多时尝试提高，并同时观察正例与负例。

**目前 Compose 没有透传这个变量。** 本机 Python 可以在根 `.env` 设置；Docker 需要先在开发和生产后端 environment 中增加下面映射，才会读取根 `.env` 的值：

```yaml
RETRIEVAL_MIN_SCORE: ${RETRIEVAL_MIN_SCORE:-0.35}
```

本轮只提供方案，没有修改 Compose 的阈值映射。返回来源里的 `score` 已是 RRF 分数，不能拿它与 0.35 比较，更不能把它当成模型判断的可信度。

## 3. 目前写在代码中的边界

| 项目 | 当前实现 | 调整位置与影响 |
| --- | --- | --- |
| 分块 | 默认 700 字符，步长 600，重叠 100；按页切片。上传 Markdown 可显式指定 `chunk_strategy=markdown_sections`，先按标题隔离小节再切块 | `rag/parser.py:parse()`；新策略只影响新上传文档，需重新导入、嵌入和索引，不会迁移旧文档 |
| 父块 | 同页相邻最多 3 个叶子组成父块；新小节策略同时禁止跨小节合并 | `rag/hierarchy.py:attach_parents()`；调整后需重建父子关系，普通索引升级脚本不能代替任意分块策略迁移 |
| 重叠合并 | 最多查找 100 字符的相邻重叠 | `rag/hierarchy.py:join_overlaps()`；改变解析重叠时要同步检查 |
| 召回融合 | 等权 RRF，平滑常数 60 | `rag/retrieval.py:rrf()`；图谱再与已融合的普通候选做一次排名融合，不是三路原始得分直接相加 |
| 最终来源 | 最多 5 条，加总字符限制 | `rag/retrieval.py:pack_evidence()`；修改需要同步评测 K 范围及聊天引用、页面和相关测试 |
| 查询路由 | 规则判断复杂度，最多 4 子查询 | `rag/pipeline.py:local_plan()`、`rag/contracts.py`；更适合先观察真实失败题，再修改规则 |
| 图谱抽取 | 每份最多 64 块，每块最多 12 个实体、12 条关系 | `rag/graph.py:build_graph()`、`Extraction`；超限明确失败；提高上限要同时核算抽取耗时和费用 |
| 图谱遍历 | 最多 2 跳，8 个种子，每跳 32 个节点，每节点 8 条关系 | `rag/graph.py:graph_recall()`；尚未提供环境变量，不建议首轮直接扩大跳数 |
| 图谱实体匹配 | 完整名称或已抽取别名文本匹配 | `rag/graph.py:matches()`；名称不匹配时，先补正原文明示别名并重建图谱，扩大跳数无法解决种子未命中 |
| 向量索引 | COSINE + AUTOINDEX；稀疏 BM25 使用 jieba | `rag/embeddings.py:VectorIndex.ensure()`；目前没有可在 `.env` 调整的 HNSW ef 或 BM25 k1/b。修改 schema 或分析器要做索引版本升级 |

不要只修改 `EMBEDDING_DIMENSION`，它必须与实际模型输出一致。本地模型由 `BGE_MODEL_PATH` 指向缓存，修改 `EMBEDDING_MODEL` 字符串不等于已经更换权重。

已有 `scripts/rebuild-rag-index.py` 是**复用旧向量升级旧稠密索引到当前混合结构**的工具；它不支持换模型后重算向量，也不支持任意新分块策略。换模型或切块后应走完整重新索引，先小范围验证，旧证据 ID 标注也需同步更新。分块、schema 变化还要同步更新索引／策略版本身份，避免新旧资料混用。

## 4. 按失败现象选择调整

| 现象 | 先核对 | 优先动作 |
| --- | --- | --- |
| 正确文件一直找不到 | 文档是否 ready、是否属于所选库、索引模型版本是否一致、旧集合是否只有 Dense | 先修状态或索引兼容问题，再试候选 24→36、Dense 阈值 0.35→0.30 |
| 找到文件但缺少所需句子 | 原文解析是否完整、引文是否跨块、是否被 5000 字符截断 | 先试上下文 6500；仍有跨段断裂再考虑按标题／段落切块 |
| Hit 很高但多跳完整率低 | 是否两端证据都标注、图谱 ready、实体能否命中、第二份证据是否被父块或前五条挤掉 | 对照图谱开关、候选数和父块比例，不直接扩大跳数 |
| 正确证据在候选里但排名靠后 | 当前是搜索接口还是聊天路径、重排是否真正 applied | 在完整聊天评测中比较重排；只跑本脚本不能评出其增益 |
| 无关问题也能找出来源 | 无答案问题标注、Dense/BM25/图谱各自的命中 | 阈值仅能控制 Dense；聊天拒答还需核对 Grader，检索空结果不等于拒答正确 |
| 有正确证据却回答“没有相关知识” | Grader 输入长度、路由、真实模型输出，是否只传了每条前 800 字符 | 先定位评分证据是否被截断，再考虑评分模型或输入组织，不能只调召回数量 |
| P95 高、经常失败 | Embedding 冷启动、GPU/CPU、检索并发、模型重试、重排 fallback | 分阶段看耗时，资源不足时减并发；不要先无条件扩大总超时 |

图谱目前只提供候选，不保证把一条多跳路径的全部证据作为不可拆分组合保留。若两跳关系已完整找出却总在最终打包时丢掉一条，需要设计路径证据成组打包，这是代码改进，调 `.env` 只能缓解，不能保证解决。

## 5. 建议第一轮实验顺序

1. **基线**：源码默认参数，记录实际服务配置；图谱若未构建，先以关闭图谱作为明确基线。
2. **候选数**：仅将 `RAG_CANDIDATE_LIMIT` 从 24 改为 36；有收益再试 48。若召回不升而 P95 增加，保留较小值。
3. **字符预算**：固定最优候选数，仅把 `RAG_CONTEXT_CHARACTERS` 从 5000 改为 6500，针对被截断的证据观察变化。
4. **父块合并**：固定前两项，比较 `RAG_MERGE_RATIO=0.5` 和 `0.8`。三子块父块在 0.5 时通常命中 2 块即可合并，0.8 时要 3 块；往下调到 0.3 仍受至少 2 块限制，未必有效。
5. **图谱对照**：保证图谱已构建后，比较开关，重点看跨文档题的完整证据命中率、同名误命中与额外耗时。
6. **Dense 阈值**：仅在确认透传后比较 0.30／0.35／0.40，并同时检查负例。没有统一最佳阈值。
7. **聊天重排与评分**：检索证据质量稳定后，再单独做真实聊天对照，观察答案事实正确性、原文支持、误拒答、耗时及调用成本。

第一轮通常无需换 Embedding 模型。若后续要尝试切块，先比较“当前固定 700 字符”和“按标题／段落、保留标题上下文、限制最大长度”的小规模样本；不要直接重建全部业务资料。

建议每组报告单独保存在 baseline、candidate36、context6500、merge08、graph-on 等目录，另记录改动值、服务版本、是否重启、索引版本和运行时间。根据实际业务设定召回、负例、P95 和成本门槛，使用验证集确认收益后再保留设置。
